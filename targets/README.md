# targets：目标状态库

`targets/` 描述所有 Omarchy 电脑最终应该达到的状态。它只保存目标数据；如何修改系统、如何更新目标库由 `workflows/` 定义。

## 主题原则

1. 一个主题一个文件，存放在 `targets/topics/`。
2. 主题按用户可感知的行为划分，不按配置文件、软件包或插件划分。
3. 同一功能的后续变化更新原主题文件，不新建重复主题。
4. 单个主题建议不超过 150 行；超过时继续按用户可感知行为拆分。
5. `INDEX.md` 只做导航，不承载细节。
6. 当前只有 Omarchy 一个平台；未来出现第二平台时再重新设计层级。

## 状态语义

- `Stable`
  - 目标和方案稳定，可作为默认复现目标。
  - 只表示设计稳定，不代表每台机器都已经应用。
- `Experimental`
  - 仍在试验；未经用户明确要求，不得默认应用。
- `Draft`
  - 目标尚未确定，只用于记录想法。

`最后验证` 是最近一次在任意目标机器上验证通过的日期。

## 主题文件格式

```markdown
# <主题名>

- **分类**: <输入法 / 桌面体验 / 应用兼容 / 显示 / 服务>
- **状态**: <Stable / Experimental / Draft>
- **适用范围**: Omarchy
- **最后验证**: <YYYY-MM-DD>

## 目标状态
- <用户最终希望得到的行为>

## 关键方案
- <涉及文件、软件包、插件或命令>

## 硬件/环境差异
- <需要检测的内容，以及不能直接照抄的原因>

## 经验教训
- <反复调试后才发现的关键原因和正确思路>

## 验证
- <完成后应检查什么，以及期望结果>
```

## 应用兼容主题要求

针对具体应用的兼容性目标（例如微信缩放和输入法问题）必须额外写清：

1. **应用与别名**：中文名、英文名、包名、常用命令名；便于 `AGENTS.md` 的检索规则命中。
2. **验证版本**：应用版本、Omarchy/Hyprland 版本、输入法版本；无法稳定复现时不得标记 `Stable`。
3. **组合问题**：如果问题涉及多个子系统（如显示缩放 + 输入法），目标状态和验证必须同时覆盖所有子系统。
4. **启动方式**：desktop entry、启动命令、环境变量、是否 XWayland/Qt/GTK 等必要信息。
5. **适配条件**：不同分辨率、缩放、输入法或应用版本下的检测和决策方法。

例子：缩放修复后必须继续验证输入法候选窗和中文提交，不能只看界面大小。

## 硬件要求

1. 目标库同步“意图”，不复制某台机器的具体硬件值。
2. 显示器名、分辨率、缩放、GPU、声卡、网络接口、外接键盘等必须写明检测方法。
3. 无法可靠适配时不得标记 `Stable`。
4. 被后续方案取代的做法只保留在“经验教训”，不得保留在“目标状态”。
