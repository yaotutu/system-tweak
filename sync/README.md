# 同步配置规范

本目录保存需要在 Omarchy 电脑之间复现的“目标状态文档”，不是变更流水账。

## 设计原则

1. 一个主题一个文件，不要把所有设置写进一个大文档。
2. `INDEX.md` 只做导航，不承载细节。
3. 所有主题都位于 `sync/topics/` 下；当前只有 Omarchy 一个平台。
4. 主题按“用户可感知的行为”划分，不按配置文件、插件或软件包划分。
5. 同一功能的后续变化更新原文件，不新增重复主题。
6. 单个主题文件建议不超过 150 行；超过时按用户可感知的行为继续拆分。
7. 涉及硬件差异的内容写“先检测再适配”，不直接复制本机值。
8. 敏感信息不入库。
9. 不创建额外的同步 changelog；文件历史由 Git commit 记录。

## 状态语义

- `Stable`
  - 目标状态和实现方案已经稳定，可以作为默认复现目标。
  - 只表示设计意图稳定，不代表每台机器都已经成功应用。
- `Experimental`
  - 方案仍在试验，不应默认应用到所有机器。
- `Draft`
  - 目标尚未最终确定，只用于记录想法。

`最后验证` 表示最近一次在任意一台目标机器上验证通过的日期。

## 主题文件格式

```markdown
# <主题名>

- **状态**: <Stable / Experimental / Draft>
- **适用范围**: Omarchy
- **最后验证**: <YYYY-MM-DD>

## 目标状态
- <用户最终希望得到的行为>

## 关键方案
- <涉及文件、软件包、插件或命令>

## 硬件/环境差异
- <需要检测的内容，以及不能直接照抄的原因>

## 经验教训
- <反复调试后才发现的关键原因和正确思路>

## 验证
- <完成后应检查什么，以及期望结果>
```

## 硬件适配原则

1. 同步意图，不盲目同步本机硬件值。
2. 必须先运行 `hyprctl monitors`、`hyprctl all`、`lsblk`、`lspci` 等适合当前主题的检测命令。
3. 根据检测到的实际显示器、GPU、声卡、网络接口或键盘情况适配。
4. 低风险、与硬件无关的规则可以直接应用；可能改变用户交互或影响安全的内容，应先向用户确认。
5. 如果无法确定，先报告检测结果和建议方案，不要直接覆盖。

## 维护规则

1. 新增主题前先检查 `INDEX.md`，确认没有已有主题可以承载。
2. 新增主题后必须同步更新 `INDEX.md`。
3. 修改主题前先在本机执行 `git pull --rebase`，避免多机器并发修改造成冲突。
4. 修改主题前先对比本机 `logs/`、系统实际状态和 `sync/`。
5. 用户明确同意后才能新增、修改或删除主题。
6. 如果一个主题超过 150 行，优先拆分为更小的主题文件。
7. 被后续方案取代的旧做法只保留在“经验教训”，不保留为目标状态。
8. 修改完成并验证通过后，执行 `git commit`；配置远程仓库后执行 `git push`。
