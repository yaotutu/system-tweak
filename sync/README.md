# 同步配置规范

本目录保存需要跨电脑复现的“目标状态文档”，不是变更流水账。

## 权限规则

1. 本文件定义同步文档的格式和收录标准。
2. 任何具体配置条目都必须经过用户明确同意后才能加入。
3. AI 不得因为本地日志中存在某个变更，就自动把它加入同步文档。
4. 新增、修改或删除同步条目，都必须先获得用户明确同意。
5. 本地日志 `logs/` 永远不作为同步内容。
6. 用户可以在每次任务完成后选择：
   - 不同步：只保留本机配置和本地日志；
   - 同步为通用配置：加入 `sync/universal.md`；
   - 同步为平台配置：加入对应平台文档，例如 `sync/platforms/omarchy.md`；
   - 仅本机适用：不加入 `sync/`，必要时只写入本地日志。

## 目录结构

- `sync/universal.md`
  - 所有目标电脑都适用的通用配置。
- `sync/platforms/<platform>.md`
  - 仅适用于特定平台或桌面环境的配置。
  - 例如 `omarchy.md` 对应 Omarchy / Arch Linux / Hyprland。
- `logs/YYYY-MM.md`
  - 本机历史日志，不同步。

## 条目格式

编号采用全局递增的 `SYNC-001`、`SYNC-002` …；不复用、不重排已有编号。

新增条目时，按下面的格式写入对应文档：

```markdown
## SYNC-<编号> · <一句话标题>

- **范围**: <通用 / 平台:Omarchy>
- **状态**: <✅ 已验证 / ⚠️ 待验证 / 🧪 实验>
- **问题**: <一句话说明要解决什么问题>
- **目标状态**:
  - <用户最终希望得到的行为>
- **关键方案**:
  - <为了达到目标状态，应如何配置；必要时写涉及文件、软件包或服务>
- **硬件/环境差异**:
  - <哪些值必须先检测；哪些内容不能在不同电脑上直接复制>
- **经验教训**:
  - <反复尝试后才发现的关键原因、坑和正确思路；
     只保留能防止再次走弯路的结论，不逐条回放失败历史>
- **验证**:
  - <完成后应检查什么，以及期望结果>
```

## 记录原则

### 要记录

- 最终目标状态。
- 问题本身和用户期望的效果。
- 关键方案和配置思路。
- 能防止再次踩坑的失败结论。
- 需要检测的硬件或环境差异。
- 可以复现的验证方法。

### 不要记录

- 密码、Token、密钥、Cookie。
- 一次性调试过程和所有无效尝试。
- 本机专属硬件值，除非同时说明了如何在新电脑上检测。
- 与最终状态无关的历史操作。
- 敏感路径、私人数据和未确认的猜测。

## 好的“经验教训”写法

写“为什么后来这样改才对”，而不是把每次失败都列一遍。

例如：

> Fcitx5 自身的 Shift 切换会先拦截按键，导致 Rime 收不到按下事件；
> 因此需要清空 Fcitx5 的临时切换键，让 Shift 交由 Rime 的 Lua 处理器处理。

这种记录能帮助之后的 AI 避免重复走弯路。

## 新电脑上的执行规则

1. 先读取 `AGENTS.md` 和本目录所有文档。
2. 先检查当前系统状态，不要直接覆盖。
3. 已经满足的条目只做验证，不重复修改。
4. 硬件相关内容必须先检测当前机器。
5. 任何实际系统修改完成后，立即写入新电脑自己的 `logs/YYYY-MM.md`。
