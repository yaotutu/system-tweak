# update-targets：把已验证配置写入目标库

## 边界

本工作流用于把某台电脑上已经验证成功的最终行为，提炼为所有电脑共享的目标状态。

会修改：

- `targets/topics/*.md`；
- `targets/INDEX.md`。

不会修改：

- 当前电脑的系统配置；
- 其他电脑的系统配置；
- 本机 `logs/`。

日志：

- 不写系统日志，因为没有实际变更系统。

Git：

- pull → 修改 → commit → push（如已配置远程仓库）。

## 触发条件

必须同时满足：

1. 该行为已在某台电脑上验证成功；
2. 用户明确同意把它作为所有电脑的目标状态；
3. 能描述清楚目标行为和验证方法。

如果系统还没有修改成功，先执行 `workflows/change-system.md`。

## 输入

必须对比三方信息，不能只看日志：

1. 本机 `logs/`：提取调试经验。
2. 当前系统真实状态：确认最终方案。
3. 当前 `targets/INDEX.md` 与主题：决定更新已有主题还是新建主题。

## 主题归属

1. 优先更新已有主题；只有新的独立用户行为才新建主题。
2. 主题按用户可感知的行为划分，不按文件、包或插件划分。
3. 单个主题建议不超过 150 行；超过时继续拆分。
4. 无法稳定复现时使用 `Experimental` 或 `Draft`，不得标记 `Stable`。

## 流程

1. 确认仓库工作树干净；已配置远程时先 `git pull --rebase`。
2. 向用户说明将写入的主题、状态和边界。
3. 新建或更新 `targets/topics/<topic>.md`。
4. 更新 `targets/INDEX.md`。
5. 检查链接、章节和硬件适配描述。
6. `git diff --check`。
7. 提交：

   ```bash
   git add AGENTS.md README.md targets workflows
   git commit -m "<描述目标更新>"
   ```

8. 已配置远程仓库时执行 `git push`。

## 记录要求

`目标状态` 只写最终行为。

`关键方案` 写持久配置、软件包和插件要求，不写一次性调试过程。

`经验教训` 只记录防止再次走弯路的结论，不逐条回放失败尝试。

`硬件/环境差异` 必须说明检测与适配方法，不能直接复制当前机器的硬件值。

## 完成判定

同时满足以下条件才视为完成：

1. 目标主题和 `targets/INDEX.md` 已更新。
2. 链接、章节和硬件适配描述检查通过。
3. `git diff --check` 通过。
4. Git 已提交；已配置远程仓库时已推送。

未推送且未配置远程仓库不阻塞任务完成，但完成报告必须提示用户提供远程地址。

## 完成报告

不得静默结束。必须向用户说明：

- 新建或更新了哪些主题；
- 为什么这样划分；
- 记录了哪些关键经验；
- 哪些内容未入库，原因是什么；
- Git 提交和推送结果。

下一步提示：

- 如已配置远程仓库，告知用户其他电脑可执行 `git pull` 后运行 `apply-targets`。
- 如尚未配置远程仓库，主动询问用户是否现在提供私有远程仓库地址。
