# sync-capture：把已验证配置提炼进同步库

## 适用场景

在用户明确同意后，把本机已经验证成功的配置整理为跨电脑可复现的目标状态。

典型请求：

- “把这个配置加入同步。”
- “更新 sync 文档。”
- “这个设置以后所有电脑都要有。”
- “把日志里的最终方案整理进同步配置。”

## 不适用

- 把 `sync/` 应用到某台电脑：改用 `skills/sync-apply.md`。
- 只修改系统但不决定是否同步。
- 只读查询、诊断或浏览日志。

## 输入

必须对比三方状态，不能只看日志：

1. 本机 `logs/YYYY-MM.md`，了解变更历史和调试经验。
2. 当前系统真实状态，确认最终方案仍然有效。
3. `sync/INDEX.md` 与现有主题，确认应更新还是新建。

## 前置工作

1. 确认仓库工作树干净；有未提交变更时先向用户说明。
2. 如已配置远程仓库，先执行：

   ```bash
   git pull --rebase
   ```

3. 向用户说明将要处理的配置、建议的主题归属和状态。

## 主题划分

1. 按“用户可感知的行为”划分，不按配置文件、软件包或插件划分。
2. 属于已有主题的后续变化，更新原主题文件，不新建重复文件。
3. 只有新的独立用户行为才新建主题。
4. 单个主题建议不超过 150 行；超过时继续按用户可感知行为拆分。
5. 无法稳定复现或仍在试验的方案标记 `Experimental` 或 `Draft`，不得冒充 `Stable`。

例子：`Ctrl+Left/Right`、`Super+Tab`、`Super+Shift+Tab` 都属于 Workspace 导航，应放在同一个主题中；不要按 Hyprland、Mirador 或键位文件拆成多个主题。

## 写入格式

主题文件必须放在 `sync/topics/`，并使用 `sync/README.md` 定义的格式：

```markdown
# <主题名>

- **状态**: <Stable / Experimental / Draft>
- **适用范围**: Omarchy
- **最后验证**: <YYYY-MM-DD>

## 目标状态
- <用户最终希望得到的行为>

## 关键方案
- <涉及文件、软件包、插件或命令>

## 硬件/环境差异
- <需要检测的内容，以及不能直接照抄的原因>

## 经验教训
- <反复调试后才发现的关键原因和正确思路>

## 验证
- <完成后应检查什么，以及期望结果>
```

`目标状态` 只写最终行为，不写历史过程。

`关键方案` 写达到目标所需的持久配置、包、插件和入口，避免把一次性调试命令写成目标状态。

`经验教训` 只记录防止再次走弯路的结论，不逐条回放失败尝试。

## 硬件处理

- 只同步意图，不直接同步本机硬件值。
- 显示器名、分辨率、缩放、声卡、GPU、网络接口等值必须写成“先检测再适配”。
- 如果目标必须依赖具体硬件，先说明检测条件和推荐决策。
- 无法可靠适配时，不加入 `Stable`；先标记 `Experimental` 或 `Draft`。

## 禁止事项

- 未经用户明确同意，不得修改 `sync/`。
- 不得修改系统配置；本 skill 只维护同步文档。
- 不得把历史日志当流水账复制进 `sync/`。
- 不得把废弃的中间方案写成目标状态。
- 不得提交真实配置文件整份内容。
- 不得提交密码、Token、密钥、Cookie 或私人数据。

## 完成标准

1. 主题文件内容完整，章节齐全。
2. `sync/INDEX.md` 已更新。
3. 主题链接有效。
4. 未同步的内容已明确说明原因。
5. 工作树检查通过：

   ```bash
   git diff --check
   ```

6. 提交变更：

   ```bash
   git add README.md AGENTS.md sync skills
   git commit -m "<描述本次同步目标>"
   ```

7. 配置远程仓库后执行：

   ```bash
   git push
   ```

## 输出给用户

- 新建或更新了哪些主题。
- 为什么这样划分。
- 记录了哪些关键经验。
- 哪些内容没有同步，原因是什么。
- Git 提交结果。
